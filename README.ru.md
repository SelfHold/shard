# Shard

[English](README.md) · **Русский**

[![CI](https://github.com/SelfHold/shard/actions/workflows/ci.yml/badge.svg)](https://github.com/SelfHold/shard/actions/workflows/ci.yml)
[![License: GPL v3](https://img.shields.io/badge/license-GPLv3-blue.svg)](LICENSE)

Синхронизация файлов между устройствами на Linux и Android без сервера посередине.
Данные раскладываются по нескольким облачным хранилищам, которые у вас уже есть
(Google Drive, Mega, S3, WebDAV, Dropbox, OneDrive, Яндекс.Диск и всё, что
поддерживает rclone, в том числе несколько аккаунтов одного типа), с избыточностью
Reed-Solomon k+m (m=1 работает как RAID 5). Всё шифруется и расшифровывается только
на ваших устройствах. Ещё в Shard есть сейф паролей, и другие приложения
[SelfHold](https://github.com/SelfHold) синхронизируют через него свои настройки.

Раньше Shard назывался CloudSync; некоторые идентификаторы по-прежнему используют
старое имя (Go-модуль `cloudsync`, бинарники `cloudsyncd`, файл vault `vault.cs`,
папка настроек `cloudsync/`, Android-пакет `dev.cloudsync.cloudsync`).

**Статус:** ранний личный проект. Опубликованных релизов пока нет, а до 1.0 формат
данных в хранилищах и API могут меняться. Собирайте из исходников (см. ниже).

## Возможности

- **Без сервера.** Устройства общаются только с хранилищами. Дерево файлов —
  детерминированная свёртка журналов операций всех устройств.
- **Сквозное шифрование.** Хранилища видят только объекты со случайными именами: ни
  имён файлов, ни размеров отдельных файлов, ни содержимого.
- **Переживает потерю хранилища.** Каждый блок делится на k частей данных и m частей
  чётности, по одной на хранилище. Пропасть могут любые m хранилищ; `repair`
  восстанавливает недостающее.
- **Файлы по запросу.** Полный список файлов есть всегда; содержимое скачивается при
  чтении, только нужные чанки. Файлы и папки можно закрепить, чтобы они были доступны
  офлайн.
- **Смонтированная папка** на Linux (FUSE); системный выбор файлов на Android.
- **Блокировки на запись** между устройствами: файл, открытый на одном устройстве, на
  других открывается только на чтение. Одновременные офлайн-правки превращаются в
  конфликтные копии, а не в потерянные правки.
- **Сейф паролей** с паролями, SSH-ключами, web3-ключами (Ethereum/EVM, Solana),
  серверами и 2FA-кодами (TOTP) с кодами восстановления; синхронизируется так же, как
  файлы. Импорт из KeePass, Bitwarden, браузеров и других менеджеров паролей.
- **Подключённые приложения.** Другие приложения (например, Parley) могут хранить в
  vault свои настройки: одинаковые на всех устройствах, во всех хранилищах, без
  собственного пароля.

## Платформы

- Целевые платформы — **Linux** (десктоп-приложение, демон, CLI) и **Android**
  (приложение с ядром внутри).
- **macOS и iOS** запланированы; платформенные особенности держатся за небольшими
  границами (`mobilebind`, поиск папки данных, Kotlin-обвязка), чтобы их можно было
  добавить позже.
- **Windows не поддерживается.** Часть кода и целей сборки для Windows осталась в
  дереве, но сборки под Windows не сопровождаются и не тестируются.

## Модель безопасности вкратце

- Vault (`vault.cs`, Argon2id) открывается одним паролем. В нём лежит мастер-ключ; все
  остальные ключи (содержимое, имена объектов, журналы, сейф, подключённые приложения)
  выводятся из него.
- Хранилища видят только шифротекст под HMAC-именами: ни имён файлов, ни размеров
  отдельных файлов, ни полей записей. Данные запечатываются XChaCha20-Poly1305.
- На устройстве сейф и журналы тоже лежат на диске зашифрованными; логи и ошибки RPC не
  содержат токенов, паролей и ключей. Содержимое файлов, которые вы открываете или
  закрепляете, хранится в кэше устройства расшифрованным (как у любой синхронизируемой
  папки), поэтому защищайте само устройство шифрованием диска.
- Ключи и доступы к хранилищам есть только в Go-ядре; Flutter-интерфейс получает
  секрет, только когда пользователь его открывает. На десктопе приложение общается с
  локальным демоном через сокет, доступный только пользователю, с bearer-токеном; на
  Android ядро работает внутри приложения.
- Подключённые приложения видят только свои записи и те части сейфа, которые
  пользователь им явно разрешил (scopes), на каждом устройстве отдельно и с
  возможностью отозвать.

Как сообщить об уязвимости — в [SECURITY.md](SECURITY.md); чего модель не покрывает — в
разделе [Ограничения сейчас](#ограничения-сейчас).

## Как это устроено

```
файл → чанки FastCDC (~4 МБ; мелкие файлы пакуются вместе)
     → XChaCha20-Poly1305 → Reed-Solomon k+m → по одному шарду в хранилище
```

- **Vault** (`vault.cs`) — единственный файл конфигурации: мастер-ключ, k/m,
  хранилища с доступами, устройства. Зашифрован ключом из вашего пароля (Argon2id).
  Копия лежит в каждом хранилище, чтобы изменения (например, новое хранилище) доходили
  до других устройств.
- **Хранилище определяется своим `id`, а не типом**: два аккаунта Mega — это два
  независимых хранилища. Поле `domain` (по умолчанию — тип) — зона отказа: шарды
  одного блока раскладываются по разным провайдерам, а `status` предупреждает, если
  потеря одного провайдера сделает файлы нечитаемыми.
- **Индекс без сервера.** Каждое устройство пишет только свой журнал операций
  (`j/<device>/<seq>`, зашифрован, копия в каждом хранилище). Дерево файлов —
  детерминированная свёртка всех операций (Lamport-часы). Параллельные правки одного
  файла дают конфликтную копию, а не потерю данных.
- **Файлы по запросу.** Пины (`cs pin`) держат файлы или папки на устройстве;
  `pin /` хранит полную локальную копию — *опорное устройство* (переключатель в
  «Обслуживании»). Приложение закрепляет в фоне (прогресс в `Status`); `cs pin` и
  `cs sync` дожидаются этого.
- **Блокировки.** Открытие файла на запись ставит lease во все хранилища. Устройство
  владеет файлом, если на большинстве хранилищ кроме его lease нет других. Пока файл
  открыт на одном устройстве, на других он открывается только на чтение. Lease истекает
  без продления (2 мин), так что пропавшее устройство не блокирует файл. Решение
  принимается, как только набрано большинство, поэтому медленное хранилище не задерживает
  открытие. После закрытия файла lease держится ещё 30 с, чтобы повторное сохранение не
  брало блокировку заново.
- **Скорость.** Все хранилища опрашиваются параллельно, к каждому — не больше 6
  запросов одновременно. Запись в журнал возвращается, когда копии есть на m+1
  хранилищах; остальные дописываются в фоне. Блоки файла загружаются по 4 одновременно.
  Чтение берёт шарды с хранилищ, которые отвечали быстрее (время отклика видно на экране
  хранилищ), и запрашивает ещё один шард, если хранилище отвечает намного дольше
  обычного. При последовательном чтении следующие 2 блока скачиваются заранее.
- **Обслуживание.** `repair` читает каждый шард (с проверкой контрольных сумм),
  дописывает потерянные, переносит их с отключённых хранилищ, перекодирует блоки после
  смены k/m (новое «поколение» шардов с новыми именами) и может перераспределить данные
  по новым хранилищам. `gc` удаляет объекты, которые ни одному файлу не нужны дольше
  7 дней (каждое устройство ведёт свой отсчёт, договариваться не нужно). Журнал каждое
  устройство упаковывает само: каждые 64 сегмента — в один объект.
- **Сейф паролей.** Пароли, SSH-ключи и web3-ключи (Ethereum/EVM, Solana) в группах с
  картинкой и именем. Запись — операция `secret` в тех же журналах устройств, поэтому
  синхронизируется как дерево файлов (одновременные правки дают конфликтную копию
  записи). Внутри операции две части зашифрованы отдельными ключами, выведенными из
  мастер-ключа: метаданные (название, логин, URL, публичный ключ, адрес) открываются для
  списка, а секреты (пароль, заметки, приватный ключ, пароль ключа) — только когда
  открыта карточка записи. На диск (журналы, их локальные копии, `state.json`) попадает
  только шифротекст. Публичный SSH-ключ, его отпечаток и web3-адрес ядро вычисляет из
  приватного ключа само.
- **2FA-коды (TOTP).** Запись `totp` в том же сейфе: секрет (base32 или ссылка
  `otpauth://totp/…`), алгоритм, число цифр, период и коды восстановления лежат в
  зашифрованной части. Текущие коды считает ядро (`TotpCodes`); секрет в список не
  уходит. Коды восстановления вставляются как есть (нумерация, колонки, заголовки и
  примечания файла отбрасываются); использованный код удаляется из записи
  (`UseRecoveryCode`) на всех устройствах. «Импорт из ссылки» принимает ссылки
  `otpauth://totp/…` (несколько сразу) и экспорт Google Authenticator
  (`otpauth-migration://`, все части экспорта; ядро разворачивает их в `ReadTotpLinks`);
  HOTP не поддерживается.
- **Импорт из других менеджеров паролей** («Импорт» в сейфе, `ImportSecrets`): база
  KeePass (`.kdbx` 3/4 с паролем и необязательным файлом-ключом; корзина пропускается),
  KeePass XML, незашифрованный JSON Bitwarden и CSV-экспорт KeePass, KeePassXC,
  Chrome / Edge / Brave / Opera, Firefox, Safari / Apple Passwords, Bitwarden,
  1Password, LastPass, Dashlane, Proton Pass, NordPass или любой CSV с колонками
  названия / URL и пароля. Ядро читает файл (для предпросмотра ничего не записывается),
  сохраняет папки как группы (или складывает всё в одну группу), переносит
  дополнительные поля в заметки, делает отдельную 2FA-запись из поля TOTP и пропускает
  записи, которые в сейфе уже есть, поэтому повторный импорт того же файла ничего не
  добавляет. Все записи попадают в один коммит.

- **Подключённые приложения** ([docs/CONNECTOR.md](docs/CONNECTOR.md),
  `proto/connector.proto`). Приложение сопрягается с Shard один раз на устройстве: оно
  показывает 6-значный код, пользователь видит тот же код в Shard («Подключить
  приложение?», Vault → Подключённые приложения или `cs apps approve`) и разрешает.
  После этого приложение хранит в vault небольшие записи (≤ 256 КиБ, например свой файл
  настроек). Запись — операция `app` в журналах устройств, зашифрованная ключом
  приложения. Запись делается от известной ревизии, устаревшая отклоняется.
  Одновременные записи офлайн-устройств сохраняются все, как версии записи, пока
  приложение их не сольёт, поэтому ничего не теряется. Приложение получает и свой ключ
  (`AppKey`, одинаковый на всех устройствах), чтобы защищать локальную копию без
  собственного пароля. Сопряжённое приложение видит только свои записи — не файлы, не
  пароли и не хранилища, — если пользователь не дал ему scope: `passwords` (браузеру —
  логины сайтов из сейфа), `ssh_keys` (только чтение) или `servers` (один список
  серверов на все SSH- и БД-приложения); см. § 12–14 CONNECTOR.md. В Vault →
  Подключённые приложения видно каждый scope, и каждый можно забрать отдельно. На
  десктопе API работает на отдельном сокете, адрес которого в `connector.json`; на
  Android — bound service `ConnectorService` (вызывающий определяется по пакету и
  сертификату подписи).

## Сборка из исходников

Готовых релизов пока нет. Все результаты сборки попадают в `builds/`.

Что нужно:

- **Go** (версия из `go.mod`) и компилятор C; заголовки FUSE и `libfuse.so.2` (пакет
  `fuse2` / `libfuse2`) для монтирования на Linux, либо `libfuse3.so.3` с
  `FUSE_TAGS=-tags=fuse3`.
- **Flutter** (stable; CI использует версию из `.github/workflows/ci.yml`) для
  приложения. На Linux ещё файлы разработки GTK 3, `clang`, `cmake`, `ninja`,
  `pkg-config` и `libayatana-appindicator3` (значок в трее).
- **Android:** Android SDK и NDK (ищется в `~/Android/Sdk/ndk`, или передайте `NDK=`),
  JDK 17 и `gomobile` / `gobind` (`go install golang.org/x/mobile/cmd/gomobile
  golang.org/x/mobile/cmd/gobind && gomobile init`).
- `protoc` с `protoc-gen-go`, `protoc-gen-go-grpc` и Dart-плагином
  (`dart pub global activate protoc_plugin`) — только чтобы перегенерировать код
  (`make proto`).

```bash
make build         # builds/cs, builds/cloudsyncd (Linux, FUSE 2)
make build FUSE_TAGS=-tags=fuse3   # если есть libfuse3.so.3
make build-linux   # десктоп-приложение в builds/linux (cloudsyncd рядом)
make aar           # Go-ядро для Android (gomobile AAR)
make build-apk     # APK для Android (arm64, x86_64) в builds/android; сначала собирает AAR
make app-run       # собрать cloudsyncd и запустить приложение в режиме разработки
make proto         # перегенерировать Go- и Dart-код из proto/
make vet test      # go vet + тесты Go-ядра (тесты ограничены 1 ГБ памяти)
make race          # то же с детектором гонок
make app-test      # flutter analyze + flutter test
```

Release-APK подписывается ключом из `app/android/key.properties` или из переменных
окружения `CS_KEYSTORE`, `CS_KEYSTORE_PASSWORD`, `CS_KEY_ALIAS`, `CS_KEY_PASSWORD`;
без них он подписывается debug-ключом.

## Быстрый старт (CLI)

```bash
export CS_PASSWORD=...          # иначе пароль будет спрошен
cs init -k 2 -m 1               # 2 части данных + 1 чётность: нужно ≥3 хранилищ
cs backend add -name "Mega личный" -type mega user=me@x.com pass=...
cs backend add -name "Mega рабочий" -type mega user=work@x.com pass=...
cs backend add -name "S3" -type s3 provider=AWS access_key_id=... secret_access_key=... region=eu-central-1 bucket_acl=private
cs backend add -name "MinIO" -type s3 -domain minio-home -root cloudsync \
  provider=Minio endpoint=http://nas.local:9000 access_key_id=... secret_access_key=...
cs backend add -name "Drive" -type drive token='{...}'   # token из `rclone authorize drive`
cs status
cs put ~/Documents /
cs ls -l /Documents
cs pin /Documents               # держать на этом устройстве
cs get /Documents/report.pdf .
cs repair                       # дописать потерянные шарды, перенести с отключённых хранилищ
```

Обслуживание:

```bash
cs repair [-rebalance]          # проверить всё, восстановить; -rebalance — разложить по новым хранилищам
cs redundancy -k 2 -m 2         # новая схема для новых файлов, затем cs repair
cs gc                           # удалить данные, не нужные дольше 7 дней (-grace 168h)
cs backend reconnect ID         # OAuth-токен истёк или отозван: войти в тот же аккаунт заново
```

Для `-type local` папка задаётся абсолютным `-root`. Неизвестные параметры
отклоняются.

S3-совместимые серверы (MinIO, Ceph, …): `-root` — это `bucket[/folder]`; бакет
создаётся при первой записи, если ключу это разрешено. Аккаунт S3-хранилища —
`access_key_id@хост endpoint`, поэтому двум хранилищам на одном сервере нужны разные
ключи. Дайте своему серверу собственный `-domain`: иначе он делит зону отказа `s3` со
всеми остальными S3-хранилищами.

Хранилище, у которого истёк вход (401, «invalid_grant»), сохраняет свой ID и данные: в
приложении нажмите «Переподключить» на экране хранилищ или выполните
`cs backend reconnect ID`. Вход в другой аккаунт отклоняется.

## Приложение

Одно Flutter-приложение на всех платформах, ядро одно и то же:

- **Linux.** Приложение — клиент демона `cloudsyncd`. Адрес и токен оно читает из
  `<config dir>/cloudsync/endpoint.json`. Если демон не запущен, приложение запускает
  его само: ищет рядом со своим бинарником, в `$CLOUDSYNCD` или в `PATH`. После
  разблокировки демон монтирует vault в `~/CloudSync` (меняется флагом `-mount`).
  «Открыть» в приложении открывает файл в этой папке, поэтому правки сохраняются, а файл
  на это время заблокирован. Закрытие файла не ждёт загрузки: файл сначала записывается
  в очередь на диске, потом загружается в фоне и до тех пор читается из локальной
  копии. Если демон упадёт до конца загрузки, она продолжится при следующем запуске.
- **Android.** Ядро работает внутри приложения: AAR из `make aar`, foreground-сервис,
  gRPC на unix-сокете в личной папке приложения. Vault виден в системном выборе файлов
  (DocumentsProvider). Чтение идёт потоком, скачиваются только нужные части. Запись
  берёт блокировку vault и загружает файл, когда другое приложение его закрывает.
- **Экраны:** разблокировка и первая настройка (новый vault или файл с другого
  устройства); пароли (группы, карточка записи, генератор паролей, копирование с
  очисткой буфера обмена через 30 с; режим «2FA-коды» с живыми кодами и кодами
  восстановления); файлы (загрузка, открытие, «хранить на устройстве», переименование,
  удаление, кто держит файл открытым, конфликтные копии и их разрешение, поиск);
  хранилища (состояние, мастер добавления с входом через браузер для Drive, OneDrive и
  Dropbox, отключение, удаление); обслуживание (синхронизация, «держать всё на
  устройстве», проверка и восстановление, смена k/m, очистка, устройства); vault (смена
  пароля, экспорт файла vault для нового устройства, блокировка).
- **Язык:** интерфейс запускается на английском независимо от языка системы; русский
  можно выбрать на экране Vault. Выбор хранится на устройстве и не синхронизируется.
- **Новый vault** открывается сразу, но работает только с k+m хранилищами. До этого
  приложение показывает экран хранилищ.
- **Вход через браузер** (OAuth): ядро поднимает rclone-сервер на `127.0.0.1:53682`, а
  приложение открывает ссылку. Браузер должен быть на этом же устройстве.

На новом устройстве нужен файл `vault.cs` (экспорт на экране Vault) и пароль.

Скриншоты всех экранов на 1440 и 390 px против работающего демона:
`SHOTS=/tmp/shots flutter run -d linux -t tool/screenshots.dart` (в `app/`).

## Ограничения сейчас

- Удалённые и старые версии записей сейфа остаются в журнале (зашифрованными), пока
  журнал не свёрнут в снимок. Расшифрованные пароли живут в памяти ядра и приложения,
  пока открыта карточка; Go и Dart не гарантируют затирание строк, а память может
  попасть в swap.
- Блокировки работают «почти всегда»: офлайн-устройство их не видит; такие правки
  превращаются в конфликтные копии.
- Старые версии файлов хранятся только до GC (7 дней): истории версий в интерфейсе нет.
- Журнал упаковывается, но не сворачивается в снимок дерева: история операций растёт
  (килобайты на тысячи правок).
- Вход через браузер работает, только если браузер на этом же устройстве. В CLI
  OAuth-хранилищам нужен готовый `token` из `rclone authorize`.
- На Android смонтированной папки нет: файлы видны через системный выбор файлов
  (DocumentsProvider) и в самом приложении.

## Приложения SelfHold и Connector

Shard — часть [SelfHold](https://github.com/SelfHold), набора независимых
self-hosted приложений. Каждое приложение работает само по себе; Shard — необязательный
слой синхронизации, который они используют через **Connector API**
([docs/CONNECTOR.md](docs/CONNECTOR.md), канонический опубликованный контракт):

- [Parley](https://github.com/SelfHold/parley) (раньше MegaChat): клиент чатов и
  почты; хранит в Shard свой vault настроек.
- [Postern](https://github.com/SelfHold/postern) (раньше SSH Manager) и
  [Cellar](https://github.com/SelfHold/cellar) (раньше DB Manager): инструменты для SSH
  и баз данных; через Shard делят один список серверов и SSH-ключи сейфа.
- [Enclave](https://github.com/SelfHold/enclave): личная сборка Chromium; читает и
  сохраняет логины сайтов в сейфе Shard.
- [Bezel](https://github.com/SelfHold/bezel): тема GTK / GNOME Shell в том же стиле.

Общего кода у репозиториев нет: каждый потребитель держит побайтовую копию
`proto/connector.proto`, владелец которой — этот репозиторий. Версия 1 только
добавляет поля и методы, поэтому приложения продолжают работать со старым Shard.
